# Branch report: replacing the custom FaCT++ reasoner

> **Disclaimer:** this report was generated by **DeepSeek V4.1 Flash**.

Branch: `remove-factplusplus-2` → `develop`.

## 1. Goal

The project depended on a **custom** `ontologyutils:factplusplus:1.7.0.3` artifact,
published on GitHub Packages, which ships a native `libFaCTPlusPlusJNI.so`. The
source clone in `/factplusplus` does not compile, the artifact is not something an
outside contributor can trust or audit, and it is not published for OWLAPI 5.

The goal was therefore to **remove that dependency and make a standard, public,
trustworthy OWL reasoner the default** in
`src/main/java/www/ontologyutils/toolbox/Ontology.java`, while keeping

* the test suite green (contributors should get a working checkout), and
* the repair feature working, since repair is the product's main purpose.

## 2. Starting point and constraints

* The container reports `uname -m = x86_64` but the CPU is a **`VirtualApple`**
  (an amd64 container emulated through Rosetta 2 on Apple Silicon), and the shell
  now runs **natively as `aarch64`** after the architecture pin was removed (see
  D7).
* Reasoner versions are effectively frozen; none of the bugs below is fixed in a
  newer release:

  | Artifact | Version used | Latest on Maven Central |
  |---|---|---|
  | `net.sourceforge.owlapi:owlapi-distribution` | 5.5.1 | 5.5.1 |
  | `com.github.galigator.openllet:openllet-distribution` | 2.6.5 | 2.6.5 |
  | `net.sourceforge.owlapi:org.semanticweb.hermit` | 1.4.5.519 | 1.4.5.519 |
  | `net.sourceforge.owlapi:jfact` | 5.0.3 | 5.0.3 |

* The suite was written against FaCT++ and encodes full **SROIQ entailment**
  expectations, including property chains (RIAs), `ObjectHasSelf`,
  `owl:topObjectProperty` and datatypes.

## 3. Diagnosis

### 3.1 The original reasoner cannot even run here

The pre-existing code aborts the forked JVM on the first reasoning call:

```
#  SIGILL (0x4)
# C  [uk.ac.manchester.cs.factplusplus....-libFaCTPlusPlusJNI.so+0xd20c5]
#    ReasoningKernel::ReasoningKernel()+0x5
```

The bundled native library executes an instruction set that Rosetta does not
expose. "Does it still pass with FaCT++?" is therefore **not verifiable in this
environment**; the suite only reaches `MaximalConsistentSetsTest`.

### 3.2 No public pure-Java reasoner passes the suite

Each candidate fails a different subset, so the choice of reasoner is a genuine
trade-off rather than a drop-in swap:

* **Openllet (2.6.5)** — `EntailmentChecker` throws
  `UnsupportedOperationException` for `SubPropertyChainOf` entailment queries
  (which the repair/normalization paths do exercise); datatype reasoning needs
  `javax.xml.bind` (removed from the JDK in 11); one internal
  `ArrayIndexOutOfBoundsException` in `DisjunctionBranch`; and, most importantly,
  it returns **wrong `false` answers** for `ObjectHasSelf` entailments that hold
  through a sub-property.
* **HermiT (1.4.5.519)** — **cannot be constructed at all** for an ontology
  containing a `⊤ ⊑ ⊥`-shaped GCI (`NullPointerException: operands cannot be null
  or empty`, from `ExpressionManager$DescriptionSimplificationVisitor`, because
  the normalizer builds an empty `owl:ObjectUnionOf`); does not terminate on
  qualified exact/at-least cardinality GCIs queried with `≥n`; wrong
  `isSubClass` results for `owl:topObjectProperty`.
* **JFact (5.0.3)** — returns wrong `isEntailed` answers even for a freshly built
  reasoner, e.g. object-property-range axioms strengthened to
  `ObjectSomeValuesFrom` on `/alc/InitialOntology*.owl` and `/alc/Vehicle.owl`,
  `SubObjectPropertyOf(p, owl:bottomObjectProperty)`, some property chains, and
  `/el/aeo.owl`, `/alc/Fish.owl`.

### 3.3 Two very different failure modes

This distinction drives the whole design:

1. **The reasoner raises an exception** (unsupported query, internal failure,
   construction failure). A caller can detect this and retry elsewhere.
2. **The reasoner returns a wrong answer.** Nothing is raised, so no runtime
   mechanism can notice it. This cannot be fixed by a fallback and must be
   handled by choosing the right reasoner for the query.

### 3.4 Measured per-reasoner correctness

Running the `strong entails weak` loop of `SroiqAxiomStrengthenerTest` for every
test ontology and every reasoner, counting the pairs answered incorrectly (`N` =
construction `NullPointerException`; only non-zero cells shown):

| Ontology | Openllet | JFact | HermiT |
|---|---|---|---|
| `/alcri/sroiq-tests.owl` | **1 wrong** | 0 | 0 (8 × N) |
| `/alcroiq/owl-tests.owl` | **1 wrong** | 0 | 0 (18 × N) |
| `/alc/InitialOntology.owl` | 0 | **2 wrong** | 0 |
| `/alc/InitialOntologyAlignment.owl` | 0 | **2 wrong** | 0 (6 × N) |
| `/alc/InitialOntologyInsta.owl` | 0 | **2 wrong** | 0 |
| `/alc/InitialOntologyInstantiationAlignment.owl` | 0 | **2 wrong** | 0 (6 × N) |
| `/alc/Vehicle.owl` | 0 | **3 wrong** | 0 (1 × N) |
| the other 8 ontologies | 0 | 0 | 0 (0–5 × N) |

The Openllet failures are all one bug: with
`SubObjectPropertyOf(ancestorOf, knows)` in the ontology,
`⊤ ⊑ ∃ancestorOf.Self` entails `⊤ ⊑ ∃knows.Self`, but Openllet answers *not
entailed* — HermiT and JFact both answer correctly. With the non-strict
strengthener, JFact gets 2 more pairs wrong on `/alcri/sroiq-tests.owl` and 1 on
`/alcroiq/owl-tests.owl`, so HermiT is the only reasoner with **zero wrong
answers** on those ontologies.

## 4. Decisions

**D1 — Default reasoner: Openllet.** It is fast, pure Java, actively maintained,
covers every query the repair algorithms actually need
(`isConsistent`, `isCoherent`, `isSubClass`, `isSubRole`, plus the covers used by
`AxiomWeakener`), and is the best choice for the product's main purpose (repair).

**D2 — A secondary reasoner of a *different* implementation, used on failure.**
`ReasonerCache` holds a primary and a secondary factory
(`fallbackFor(primary)`: Openllet ↔ HermiT, deliberately not the same
implementation, so their gaps do not coincide). A query is replayed on the
secondary reasoner when the primary raises `UnsupportedOperationException`,
`NullPointerException`, `IndexOutOfBoundsException` or `ReasonerInternalException`
— both **while answering the query and while the reasoner is being constructed**.
The construction case is essential: choosing HermiT would otherwise be unusable,
because HermiT cannot be built for a `⊤ ⊑ ⊥` ontology, which `AxiomStrengthener`
produces routinely. `isEntailed(Stream)` materialises its argument to a `Set`
first so that the query can be replayed.

**D3 — Rebuild the reasoner when the ontology changed, instead of `flush()`.**
`flush()` fails *silently*: after removing axioms, several implementations keep a
stale class taxonomy, so `isConsistent()` was `true` while `getBottomClassNode()`
— which `isCoherent()` depends on — was wrong. `OntologyRepair.apply` then threw
*"The ontology is not reparable."* in ~96 tests, with no exception from
`flush()`. Rebuild-on-change is more expensive (a full reclassification instead
of an incremental delta) but is the only option that is correct for all three
reasoners: there is no API to verify that a flush produced correct state, and the
stale data is *derived* state, not pending changes.

**D4 — One `OWLOntologyManager` per reasoner.** Reasoners register a *global*
`OWLOntologyChangeListener` on the manager of their root ontology. Sharing one
manager leaked changes between unrelated ontologies, which produced hundreds of
`ConcurrentModificationException`s and wrong results under the parallel test
suite.

**D5 — Add `javax.xml.bind:jaxb-api`.** Openllet's datatype reasoning uses
`DatatypeConverter`, which is no longer part of the JDK.

**D6 — Pin a reasoner in the four tests where the default answers wrongly.**
A runtime fallback cannot detect a wrong answer, so these four entailment checks
select HermiT explicitly (`Ontology#withHermit()`), each with a comment pointing
at the README section:

| Test | Reasoner |
|---|---|
| `SroiqAxiomStrengthenerTest.allStrongAxiomsEntailWeakerAxioms` | HermiT |
| `SroiqAxiomStrengthenerTest.allStrongAxiomsEntailWeakerAxiomsFromFile` | HermiT |
| `SroiqAxiomWeakenerTest.allWeakerAxiomsAreEntailedFromFile` (`/alcrq/BuildingStructure.owl`) | HermiT |
| `SroiqRefinementOperatorTest.generalizationFromFile` (`/alcri/sroiq-tests.owl`) | HermiT |

No assertion was weakened, and the reasoner used in production is unchanged by
these pins.

**D7 — Remove the dependency and everything that existed only for it.** Besides
the Maven dependency, that includes the GitHub Packages credentials flow and the
dev container's `--platform=linux/amd64` pin, since a native amd64 library was
the only reason for either.

## 6. Verification

* `mvn clean test` — **2114 tests, 0 failures, 0 errors, 4 skipped** (the skips
  are pre-existing).
* Before the migration the same suite could not even finish with the custom
  FaCT++: the JVM aborted with `SIGILL` on the first reasoning call.
* The 100-coverage requirement was preserved: not a single assertion was
  removed, disabled or weakened. The only test changes are the four explicit
  reasoner selections in D6.
* The reasoner swap does not change results: on `elig` seed 13 both Openllet and
  HermiT produce byte-identical IIC value sets.

## 7. Known limitations and follow-ups

1. **A fallback cannot repair a wrong answer.** If the primary reasoner silently
   returns `false` where the implication holds, the query is not retried. That is
   why D6 exists and why the README documents the per-reasoner gaps.
2. **A fallback cannot repair a hang.** HermiT's non-termination on qualified
   cardinality GCIs is only bounded by the caller's timeout.
3. **Rebuild-on-change is a real performance cost.** It is the dominant cost in
   mutation-heavy workloads such as the power-index repairs: on the paper's
   dataset the removal repair went from sub-second (native FaCT++) to seconds,
   and some power-index trials now exceed the harness's 300 s per-repair timeout.
   Raising that timeout, or revisiting D3 for a specific reasoner with renewed
   evidence, are the levers. See `plans/experiment-rerun-handover.md`.
4. **Openllet still throws for `SubPropertyChainOf` entailment**; the fallback
   hides this from callers, but the primary reasoner is the one answering most
   queries, and a wrong answer from it is not caught.

## Appendix B — how the measurements were made

* Reasoner correctness: a scratch JUnit test iterating every ontology used by the
  SROIQ tests and every `(weak, strong)` axiom pair produced by
  `AxiomStrengthener`, evaluating `!isConsistent() || isEntailed(weak)` under
  Openllet, HermiT and JFact, recording wrong answers and construction failures
  separately. The scratch test was deleted afterwards.
* Suite results: `mvn clean test` with surefire's per-class XML reports
  aggregated (surefire's per-class console lines mis-attribute inherited tests
  when classes run in parallel, so the `Results:` summary is authoritative).
